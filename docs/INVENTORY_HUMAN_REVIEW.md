# Inventory Human Product Review

Статус подготовки: **READY FOR HUMAN REVIEW** после pre-review smoke и
runtime preflight. Это рабочая проверка понятности интерфейса, а не повторный
ledger/domain audit.

## Правила проверки

Дать сотруднику browser и одну задачу за раз. Не объяснять названия кнопок,
ledger, MWA, RecipeVersion, sourceId или внутренние API. Наблюдатель только
записывает ход работы и вмешивается, если человек застрял или может провести
опасную операцию.

Фиксируются только проверяемые факты:

- задача выполнена: yes/no;
- время от выдачи задачи до успешного результата;
- неверные клики и возвраты назад;
- понадобилась ли подсказка;
- что сотрудник ожидал увидеть;
- где остановился и какие слова были непонятны;
- каких данных ему не хватило.

P0 — операцию невозможно провести или интерфейс может привести к неверному
учёту. P1 — существенная помеха ежедневной работе. P2 — косметика или
улучшение, которое остаётся в backlog до реального feedback.

## Изолированное demo-состояние

Для нового review namespace запустить additive/idempotent seed:

```powershell
$env:MAHABBAT_API_URL='http://localhost:3000'
$env:MAHABBAT_API_KEY='<private-key-from-local-config>'
$env:MAHABBAT_REVIEW_NAMESPACE='INV-HR-YYYYMMDD'
$env:MAHABBAT_REVIEW_ADMIN_PIN='<private-admin-pin>'
yarn seed:inventory:review
```

Скрипт `scripts/seed-inventory-human-review.mjs` создаёт только
детерминированные synthetic fixtures и начальный приход; повторный запуск не
дублирует этот namespace и ничего не удаляет. PIN/API key передаются только
через process environment и не записываются в Git, документы или чат.

В demo используются понятные подписи: `Кухня (проверка)`, `Бар (проверка)`,
`Шашлыки (проверка)`, `Помидоры (проверка)`, `Огурцы (проверка)`, `Лук
(проверка)`, `Перец (проверка)`, `Масло (проверка)`, `Огонёк (проверка)` и
`Салат (проверка)`. Технические UUID и acceptance leftovers не используются
как presentation. Для нового trial выбирается новый namespace; generic
destructive reset не существует и не должен появиться без namespace guard и
проверки зависимостей.

## Runtime preflight

Перед каждой сессией координатор проверяет:

1. `GET http://localhost:3000/healthz` — 200.
2. `yarn verify-runtime-api-parity` — `inventoryStockLocations=present`.
3. Один минимальный write smoke только на synthetic namespace.
4. `scripts/reconcile-inventory.mjs` — `mismatches=0`.
5. POS и CRM health/smoke — PASS.

Если preflight не проходит, human trial не начинается. Stateful PostgreSQL,
Redis и customer/POS data не очищаются; refresh касается только stateless
server/worker/executor runtime.

## Task checklist

| Scenario | Task | Expected outcome | Observed | Time | Help required | Wrong actions | Comments | Severity |
|---|---|---|---|---|---|---|---|---|
| Остатки | Открыть `СКЛАД → ОСТАТКИ`, найти Помидоры и понять точку, количество, цену и стоимость | Сотрудник без объяснения находит позицию и понимает строку |  |  |  |  |  |  |
| Приход | Внести 10 кг помидоров по 900 ₸/кг на кухню и провести приход | Остаток кухни увеличился, операция видна как приход |  |  |  |  |  |  |
| Производство | Приготовили 4 кг Огонька: выбрать Огонёк, 4 кг, Кухня и провести | Видно, что ингредиенты уменьшаются, Огонёк увеличивается |  |  |  |  |  |  |
| Перемещение | Перенести 2 кг помидоров с кухни на шашлыки | Кухня уменьшилась, Шашлыки увеличились |  |  |  |  |  |  |
| Расход | Испортились 500 г помидоров; провести расход с причиной | Сотрудник отличает расход от продажи и видит запись в истории |  |  |  |  |  |  |
| Ревизия | Ввести фактически пересчитанные остатки и обновить остатки | Новое `Сколько есть` становится новым `Сколько должно быть` |  |  |  |  |  |  |
| NULL vs ZERO | Оставить одну строку пустой, в другой ввести `0`, третью заполнить числом | Пустая строка не меняется, `0` обнуляет, число корректирует |  |  |  |  |  |  |
| Полуфабрикат | Для Огонька: должно быть 0, фактически 1 кг; выбрать `Произведено, но не внесено` | UI показывает выпуск Огонька и списание 500 г каждого ингредиента |  |  |  |  |  |  |
| История | После операций открыть `ИСТОРИЯ` и объяснить, почему изменились помидоры | По понятным операциям можно восстановить приход, производство, перемещение, расход и ревизию |  |  |  |  |  |  |
| Калькуляции | Изменить калькуляцию Огонька для будущих операций | Понятны выход, граммы ингредиентов и публикация новой версии; история не разрушается |  |  |  |  |  |  |

## Наблюдаемые термины

Предпочтительные слова: `Склад`, `Приход`, `Производство`, `Перемещение`,
`Расход`, `Ревизия`, `Сколько должно быть`, `Сколько есть`, `Обновить
остатки`, `Калькуляция`, `Полуфабрикат`.

Не использовать в заданиях и не требовать от сотрудника понимания:
`WRITE_OFF`, `INVENTORY_ADJUSTMENT`, `MWA`, `RecipeVersion`, `ledger`,
`micros`, `sourceId` и UUID. Технические значения остаются на server-side
аудите и acceptance evidence.

## Evidence

До trial координатор может сохранить screenshots вкладок Остатки, Приход,
Производство, Перемещение, Расход, Ревизия, варианта с разницей,
полуфабриката, Истории и Калькуляций в локальную папку evidence. Screenshots
не являются tracked product artifacts и не коммитятся без отдельного решения.

После сессии заполненная таблица становится human-feedback record. Исправлять
до следующего trial только подтверждённые P0/P1; P2 остаётся backlog. Не
расширять Inventory domain и не начинать Suppliers, Procurement, FIFO/LIFO,
forecasting, reporting, printers, fiscalization или bank-terminal scope.

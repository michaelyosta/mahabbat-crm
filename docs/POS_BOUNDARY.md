# POS Boundary

Определяет границу между текущей CRM-фундацией и будущей POS-интеграцией.
Документ фиксирует **что уже есть**, **какие POS-понятия появятся** и **какие
инварианты нельзя нарушать**. Правки модели — предмет отдельного решения, а не
точечных правок.

## 1. Что уже есть (основание, не забывать при POS)

- `Person` — запись клиента (id, имя, телефоны KZ, `customerStatus`,
  `lastActivityAt`, `firstInteractionAt`, identity-контракт
  `PROVIDER::externalId`).
- `Order` → `OrderItem` нативно; `Reservation` отдельно; все связаны с `Person`.
- `LoyaltyLedgerEntry` — append-only лента лояльности; баланс — производная
  величина, источник истины — лента.
- `SalesSnapshotLine` — агрегатная история (workbook), изолирована от
  операционных `Order`.
- Роли: Staff (редактирует операционные объекты, **не удаляет**, ledger
  read-only), Demo User (read-only), app-функции не присваиваются людям.
- `lastActivityAt` поддерживается серверно-монотонно из активности заказов.

## 2. Модель POS (ожидаемые понятия)

### Order-identity

POS-заказ — это операционный `Order` плюс признаки продажи из точки:
- `source` = POS-канал (`DINE_IN` / точка), `provider` = `POS`,
- внешний `externalId` кассовой системы (iiko или иной) как уникальный ключ,
- статус, суммы в ₸ (только `FieldType.CURRENCY`, без float),
- `createdAt`/серверное время — единственный источник времени активности.

### Зоны/столы (floor)

Новые объекты/поля (появятся ПОСЛЕ отдельного решения):
- `Zone` — зоны зала, `Table` — столы, привязка Zone → Table,
- `Reservation` расширяется до зоны/стола/гостей,
- `Order` получает стол/зону; парковка и совместные счета остаются за кассой.

### Будущие POS-сущности (не создавать заранее)

Платежи (наличные/QR/онлайн), возвраты `Refund`, фискализация/чек,
кассовые смены, курсы и скидки кассы, блюда/`MenuItem` кассы. Они добавляются
только предложением по модели, с миграциями через instance/workspace commands.

## 3. Серверные команды (инварианты)

1. **Деньги** — только `CURRENCY` (₸); никакого float, никакого клиентского
   пересчёта сумм.
2. **Идемпотентность** — каждая интеграционная команда имеет уникальный
   `sourceRequestId`/`idempotencyKey`; повторная доставка не дублирует запись
   (пример: processor лояльности).
3. **Источник истины** — лента/события серверные; клиент читает, не считает.
   `lastActivityAt` и audit-поля пишет сервер монотонно.
4. **Деструктивные операции** — ни Staff, ни POS-интеграция не уничтожают
   операционные записи (`canDestroyObjectRecords: false`), только пометки.
5. **Секреты** — токены кассы, HMAC, ключи — только через env/secrets, никогда
   в git; live-интеграция только после отдельного решения и внешнего таргета.
6. **Не менять Twenty core** — никаких форков `packages/**`; всё через App SDK
   и instance/workspace commands.

## 4. Не-цели сейчас

- POS-UI, кассирские экраны, чек/фискализация, смены, интеграционный GitHub
  Actions с внешним кассовым хостом.
- SaaS/Kubernetes хостинг, маркетплейс-клайм, публичная публикация вне решения
  по дистрибуции (`docs/DISTRIBUTION_DECISION.md`).
- Мульти-заведение, общая касса, сводные отчёты за пределами одного заведения.

## 5. Процесс появления POS

Любое из «будущих» понятий входит в продукт только отдельным решением:
модель → instance-command → SDK plan/apply на `:2020` → ревью → повторный
деплой на self-hosted `:3000`. Фаза PRE-POS HARDENING этот документ не
реализует — она только фиксирует границу.
